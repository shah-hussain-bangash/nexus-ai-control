# Disposable PostgreSQL recovery in CI

The GitHub `postgresql` job runs `backend/tests/test_ci_postgresql_recovery.py` before the full backend suite. Its XML result is uploaded alongside `docs/postgresql-ci-results.xml` in the `postgresql-tests` artifact. The full suite excludes this file in that job to avoid repeating the recovery operation. The ordinary backend job and local Windows suite run the safety cases but skip the actual database operation.

The real rehearsal requires Linux, `GITHUB_ACTIONS=true`, the existing schema-creation opt-in and the exact disposable CI service identity: PostgreSQL/psycopg, `127.0.0.1:5432`, database/user `nexus_ci`, without URL query overrides. It does not load operator Settings or `.env`. It creates three fresh databases with generated `nexus_recovery_` UUID names: a source, a successful recovery target and a deliberate-conflict target. Only names successfully created by this invocation enter its cleanup list. Neither `nexus_ci` nor an existing application database is selected as a restore/drop destination.

The source fixture migrates a fresh schema, seeds three disposable accounts, saves a prompt through the in-process API and records one explicit synthetic business receipt. After all fixture writers stop, the existing encrypted-backup path makes a custom PostgreSQL dump plus a SQLite business snapshot with an ephemeral in-memory key. The test adapts `pg_dump` invocation to the same cached `postgres:16-alpine` image used by the service, with matching runner UID/GID and a mount confined to the test directory. Only the five PostgreSQL connection variables enter the client container; passwords stay out of argv and captured tool failures use fixed errors. No customer system or live model provider is contacted.

Authentication/manifest inspection must pass without claiming a PostgreSQL restore. The SQLite recovery primitive must still reject this archive. A shared PostgreSQL snapshot gate authenticates and validates the archive through the native inspector, then requires PostgreSQL kind before exposing a dump to a restore callback. Local cases cover a wrong key, altered ciphertext, truncation, an authenticated empty manifest and a valid SQLite archive sent to this gate. No rejected case may reach the callback; input bytes and temporary-file cleanup are checked. A passing PostgreSQL container-metadata unit fixture does not prove that its dump contents are restorable SQL.

Using the genuine CI-created PostgreSQL archive, the rehearsal repeats wrong-key, ciphertext, truncation and authenticated-invalid-manifest cases before the successful restore. A spy rejects any attempted restore callback during these cases, and each failure must match its expected authentication/size/manifest category. The fresh target's public relation names/kinds/object identifiers must remain unchanged, the original encrypted input must retain its bytes, and inspection plaintext temporary directories must be removed. These checks test rejection before SQL restore, not a failed SQL operation mistaken for authentication rejection.

The valid path uses the same snapshot gate, then runs `pg_restore --single-transaction --exit-on-error --no-owner --no-privileges --dbname` against the second, freshly created database. It does not use `--create` or `--clean`; the target name is explicit and generated by this test. Restore reads its dump mount in read-only mode. The client adapter rejects a restore without the required transaction flag before launching a container. See the official [PostgreSQL 16 restore options](https://www.postgresql.org/docs/16/app-pgrestore.html) and [custom-format dump documentation](https://www.postgresql.org/docs/16/app-pgdump.html).

The third fresh database is populated only with controlled failure fixtures: a canary table/row and a deliberately incompatible `workspace_assets` table/row. The same authenticated dump must fail on that exact existing-table conflict. The adapter retains only a fixed error category for this assertion; a launch, connection, authentication or timeout error cannot count as rollback evidence. After failure, public relation names/kinds/object identifiers and both fixture tables' rows must match their pre-restore state, demonstrating that this transaction left no partially restored relations and preserved the canaries. This is a disposable failure exercise, not permission to restore over an operator database.

Before opening the recovered API, all mapped control-table records and business records must match the source by local counts/hashes. The recovered fixture is neither migrated nor seeded. Checks then cover schema readiness, anonymous access rejection, fresh owner login, staging context, the saved prompt, CSRF enforcement, a successful new write, auditor read/write permissions and receipt lookup without another dispatch. Source records/sessions, source business records and encrypted input must remain unchanged after the recovered app writes.

Finally, fixture app and auxiliary target engines are disposed and only the three databases actually created by this invocation are dropped. Cleanup failure fails the test. The client adapter rejects files outside the test directory, unexpected tool arguments and destinations outside its generated source/target pair. Unit cases cover CI identity/opt-in gates, unsafe existing names, archive rejection before callback, mount/database confinement, mandatory transaction/read-only arguments, expected-conflict classification and private-error/password handling. CI tool invocations have a 60-second timeout; this is not a measured recovery-time objective.

This rehearsal demonstrates same-release recovery for a small controlled PostgreSQL 16 fixture and a synthetic SQLite business database. It does not test customer databases, deployment secrets/IdP sessions, global PostgreSQL roles/tablespaces, large-database behavior, external connectors, actual cutover/rollback, failover, off-host/key-custody workflows or measured RPO/RTO. Existing inspection responses continue to say `postgresql_restore_verified: false`; a passing CI test does not change the meaning of an arbitrary operator archive. The production recovery workstream remains partial. The eight local synthetic drills remain unchanged and do not claim to perform this CI-only restore.
