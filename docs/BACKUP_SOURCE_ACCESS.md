# SQLite backup source access

Plaintext and encrypted backup creation share the SQLite snapshot helper. It opens each configured control/business source through an escaped absolute file URI with `mode=ro`, after checking that a regular file exists. If a source disappears before SQLite opens it, the read-only open fails instead of creating a replacement empty database. A missing source fails before the destination connection opens. SQLite operation failures return a fixed error without private paths or driver details. A failure after destination creation may retain an incomplete new snapshot; it is not a successful backup.

Source reads use ordinary SQLite locking and WAL handling. They do not use `immutable=1`: committed rows in an existing WAL must remain visible. Disposable tests retain an open but idle fixture writer, confirm its committed WAL row is copied, and verify its main/WAL bytes and logical records remain unchanged. This exercises WAL reading, not cross-database consistency with concurrent writers. The backup workflow still requires the API and worker to be stopped and explicit quiescence acknowledgement.

Tests also remove a fixture source exactly between preflight and open, verify it is not recreated and no destination opens, attempt a write through the source connection and require read-only rejection, and cover relative paths containing spaces, URI-special characters and Arabic text. No operator databases or backups are used. Read-only access does not prevent another process replacing or modifying source files, guarantee a stable path identity, or prove deployment recovery. Storage permissions, source quiescence, key custody and recovery acceptance remain operator responsibilities.
