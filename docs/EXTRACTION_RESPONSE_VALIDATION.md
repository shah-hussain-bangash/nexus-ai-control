# Validate file-extraction responses before saving them

Intake completion now normalizes the extraction process response before storing text, metadata or an error code. Previously, a non-object JSON result could raise an exception during completion, leaving the job processing until existing lease recovery ran. A new regression reproduces a null response causing that exception; with validation, the job immediately fails with `EXTRACTOR_RESULT_INVALID`, releases its lease and does not block processing the next queued file.

Successful responses require an object containing a text string. Optional metadata must be a flat object limited to `method`, `pages`, `ocr_pages`, `review_required` and `extraction_mode`. Method labels are bounded visible UTF-8 strings; page counts are strict integers within the existing 12-page limit, OCR page counts cannot exceed a supplied page count, `review_required` can only affirm review, and extraction mode is auto or OCR. Null/omitted page count remains valid for DOCX. Omitted metadata remains an empty object for existing internal callers. Metadata is descriptive, not proof of extraction quality.

Text must be valid UTF-8 without null bytes and within the existing 32 KiB byte limit. Empty/whitespace-only valid text keeps its existing `NO_EXTRACTABLE_TEXT` failure. Unexpected fields, invalid types, malformed metadata and unrecognized error codes become the fixed `EXTRACTOR_RESULT_INVALID` code rather than being persisted or raising during database completion. Known extractor/parent failure codes retain their meaning; accompanying failure text and metadata are discarded. Unknown exception details are not copied into intake results or audit entries.

Validation runs after cancellation/token checks, completion deadlines and current-author authorization. Expired or superseded work therefore keeps its existing outcome; malformed output cannot override those controls. A failed extraction clears active review text/metadata, retains its original file for an explicit retry within the existing review window and attempt limit, and never automatically publishes a source. A later valid retry still needs publication review.

This changes the internal extraction-process contract, without adding an endpoint, public request field, dependency, migration, parser timeout or retry policy. Existing DOCX/PDF and configured OCR output shapes remain supported. New parser metadata/error codes must be added to the contract deliberately. This is worker resilience and output hygiene, not malware scanning, OCR-quality acceptance, authenticated evidence or production readiness.
