# Hybrid-search completion and source access changes

Hybrid search now takes the existing workspace write-ordering lock again when its ranking worker finishes. Fresh session/context validation, source ACL/version/hash checks, receipt persistence and response construction occur in that one transaction. Document access changes and deletion use the same ordering. A source-management write cannot commit between the completion check and construction of its saved response.

Ranking itself remains outside the lock. A source change can therefore complete while the worker computes; when that change wins before completion, the search records `SOURCE_SCOPE_CHANGED`, returns no hits and does not save excerpts. When completion wins, the source change can commit afterward, and subsequent history inspection, replay and recovery apply the newer access/version state and withhold affected hits. This does not retract results already delivered before a later revocation, nor promise that permissions remain unchanged after the completion transaction commits.

The change also applies the normal POST CSRF and refreshed identity/context checks to the completion write. Existing authorization failures retain their normal errors and rollback behavior; an uncompleted receipt can remain processing until existing interruption handling applies. There is no new permission, endpoint, request field, database migration, model call, ranking rule or dependency. Existing corpus, concurrency, timeout and history limits remain in effect.

Regression tests reproduce the original narrow race on disposable data: another transaction commits a source revocation after its ACL was evaluated, while the response still contains its old excerpt. With completion ordering enabled, concurrent revoke/delete attempts hit a short test-only lock deadline and roll back; they can commit after completion, and history/replay withhold the affected result. Separate cases confirm that changes can commit during ranking and fence the entire result. The same tests run against SQLite and the disposable PostgreSQL CI database. The short lock deadline is a test mechanism, not a new application timeout setting.

This strengthens the existing local LSA/BM25 access boundary. It does not grant customer acceptance, validate neural retrieval or establish deployment readiness. No user action or migration is needed beyond updating the source and restarting NEXUS.
